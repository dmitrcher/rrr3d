# Actual GameCar stabilization at PC24 (V185)

This stage compares the original Windows `GameCar::StabilizeForce` with the Source controller path. The V113 stabilization gate exercised standalone SDK fixtures at PC53; it did not prove the actual game at its observed PC24 setting.

The original constructor and SDK actor are real. PDB-resolved fixture properties select damping, roll/pitch clamps, contact booleans and clutch states. No AI runs. Native modules are hashed, the observer embeds a build identity, and failed compilation invalidates its receipt. Temporary in-process checkpoints restore each instruction before it executes; the original files remain unchanged. Adding checkpoints preserved all previous public numerical results.

The accepted V185 scope excludes clutch. Six orientations, five angular velocities, six damping/clamp recipes and two contact booleans form 360 unique helper cases. The box-only and four-wheel inertia fixtures both pass with the actual production header at O0/O2, twice each, including the original pre-setter momentum and final quaternion/angular velocity. The sentinel damping `(-1,-1,-1)` skips the local transformation when no other stabilization request is active.

Observed arithmetic keeps float products and double register sums. The inverse matrix uses individually rounded cofactors and a single float store after its determinant sum. The Shoemake conversion likewise retains the original product/store boundaries. No physical coefficients were fitted. V185 changes four Source files and no SDK files; its flag is `RRR3D_EXPERIMENT_GAMECAR_STABILIZE_V185=1`, default off, and applies only to the game-controller boundary. The generic PC53 SDK-fixture path remains a separate measured boundary.

Actual Jolt world acceptance: 180 no-contact cases, one car with four free wheels, zero gravity/body damping/motor/brake; both repeats match original stabilization plus SDK integration. The flag-off control matches 69/180. Incoming quaternion, inverse inertia, angular velocity and actual-backend derived public momentum are checked. `addAngularVelocity` does not refresh the public cached `VehicleState`; therefore that stale snapshot is explicitly named `cached_momentum_before` and is not used as the live physical input. Live inputs come from the backend trace. Contact booleans are synthetic only in the scalar method matrix, not a claim of physical wheel contact.

Clutch cases are recorded but not accepted by this stage. V186 investigates the original mass-scaled local-Z override and its controller/session timing. Full game parity remains open, including real contacts, jump, complete `OnFixedStep`, ordinary races and promotion of the experimental profile.

The first complete regression exposed four synthetic PC53 angular-controller fixtures when PC24 was selected for any callback. That rejected 604/608 result is retained as `broad-missing-command-boundary-rejected`. The accepted implementation explicitly marks actual game commands via `VehicleDriveCommand::originalGameCarStabilization` in the Session bridge; custom SDK commands default to their existing arithmetic. This is command provenance, not fixture-name selection. The targeted four-scenario regression checks all 480 states twice.
