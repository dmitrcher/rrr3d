# Следующая проверка: геометрия границы

После заморозки v59 выполнены четыре повторных записи Windows и четыре Mac.
Каждая запись сохраняет все 600 исходных физических выборок своей платформы:
Windows совпадает с неизменным эталоном, Mac — с немодифицированным кандидатом v59.

На первом расходящемся шаге 61 оригинальный SDK подготавливает два контакта
около x=8, z=10, с ошибками ограничения -0.85218972 и -0.84952176.
Mac подготавливает четыре точки задней грани коробка около x=6.63333,
z=10.30..10.90 и отделениями около -1.366669. Положение и скорость до шага 60 совпадают.
Это подтверждённое различие подготовки геометрии до решателя сил.

В `SourceMeshManifold.h` нынешний `faceContacts` является только обёрткой
контакта грани: выбирает грань коробка по максимальной проекции нормали
треугольника; комментарий явно оставляет edge-axis контакты отдельной
generic convex обёртке. Следующая проверка — воспроизвести выбор осей SAT,
контактных граней и обрезку исходного SDK на уже сохранённых одинаковых
входах. Не заменять эту геометрию подбором мощности или трения.

Сравнение материалов/кадров контакта и порядка итераций остаётся отдельным
этапом: расхождение числа и положения точек само по себе не доказывает,
что они являются единственной причиной всей последующей ошибки.

Трассировщик только читает внутренние поля, часы используют проверенный
интегратор SDK вместо счётчика вызовов геометрии. Контакт шага 61 готовится
при счётчике интегратора 60. Сохранённое `first-contact-audit.json` проверяет
восемь полных траекторий, исходные параметры машины не меняются.

Это новая зацепка, а не исправление границы. Цель полного совпадения открыта.
